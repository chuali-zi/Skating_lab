# 三段真实花滑录像的 Java 视频验收

本次将公开比赛或热身录像提交给**隔离开发库中的正式 Java API**。上传接口、后台队列、FFprobe/FFmpeg、OpenAI Responses、观察校验和带身份验证的帧读取全部走产品代码。模型实际返回的名称为 gpt-6-luna。三段共 **39 帧、12 条可见观察、6 条待核事项**。两条描述可以讲同一种姿态在不同时间的变化，条数不能换算成正确动作数。

三份文件均由 Wikimedia Commons 摄影者 **FloweringDagwood** 以 **CC BY 4.0** 公开。使用站点提供的 480p 版本，保留完整时段，转为 H.264 MP4，移除声音。提供给模型的是 Java 选出的 JPEG 和相对于各段起点的实际时间；没有附赛事网页、运动员名字或源文件名。下表的跳种和节目名来自摄影者说明。原始视频和人物图像保存在本次本地验收目录，仓库只记录来源、指纹和匿名的结构化观察。[许可条款](https://creativecommons.org/licenses/by/4.0/)

**帧号约定。** 上表的数字帧号从 0 起算，对应服务接口。Android 面向选手显示「第 1 帧」及实际秒数，即服务端 0 号帧。对于 29.97 fps 录像，实际采样间隔可以是 0.5005 秒。不能把理想半秒时刻当成原视频每次落冰、起跳的真实时刻。已保存全部 39 个时间戳、12 条观察对应的帧号、6 条待核理由和各文件指纹，可独立核算。[本次三个实拍样本的结构化结果](evidence/public-skating-2026-11-20.json)

**过程中发现的问题。** 首轮 Amber 返回了合规结果，Deniss 首次提交失败。原始失败状态只报告通用错误，不能据此断定供应商失败的具体字段。同一 MP4 由 Java 解码器独立复查得到 13 个真实时间戳。随后在发给模型的结构化协议中直接限定数组长度，并为每个片段设置实际最大帧号，仍逐条检查升序和范围；也为解码、观察和保存阶段分别返回可操作的错误。重新运行三段均完成。人工对照又暴露了 Amber 的主体误判。现在即使老报告同时包含人体观察和「未见滑冰者」，重新打开也会提示先核查主体；下游预案会带上这一层不确定性。条件检查不能自动认出滑冰者，也无法纠正所有手臂、遮挡或跟拍误差。

**本次可以确认的能力。** 输入真实冰场录像，服务器能够取出实帧、返回带帧号的描述，运动员可以在手机中打开证据并纠正。模型自报的高置信度仍会伴随误判。三份材料来自同一摄影者，均为赛事现场单机位，未经专业裁判盲标。此测试不提供跳种、周数、用刃、降周、GOE 或个人成功率的识别准确率。

**复现方式。** 在隔离的本机开发服务开启视频观察后，运行下列命令。脚本从文件页对应的公开分辨率下载，校验 SHA-256，顺序送测；结果、逐帧 JPEG 和对照图存放在本机输出目录。每次运行都会产生实际供应商调用。[验证脚本](../scripts/verify-public-skating.ps1)

~~~powershell
.\scripts\verify-public-skating.ps1 -BaseUrl http://127.0.0.1:8080
~~~
