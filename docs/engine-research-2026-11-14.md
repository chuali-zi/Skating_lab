# Skating Lab 计算与建议引擎技术调研

调研日期：2026-11-14。产品基线：[PRD v0.8](PRD.md)。

首版用户端已确定为原生 Android，仅承担输入、上传、编辑和展示。当前技术主线为**云端 LLM + 花滑知识库/RAG + 个人长期档案 + 服务端计算工具**，检索、推理、计算和视频分析均在服务端完成。当前不训练、不微调、不采购训练 GPU，也不在用户设备部署模型。通过更新知识、案例与个人记录改善建议，模型参数保持不变。

本轮核对了论文、官方仓库、模型卡与厂商文档，没有执行模型推理或训练。花滑专用模型调研保留为参考，不是当前实施清单。用户视频、API 访问能力与教练评估样本尚未在本轮建立；下一步验证 RAG 是否改善知识使用和个人建议，不开展模型训练。

## 决策范围

| 状态 | 内容 |

## 云端 RAG 教练引擎

RAG 在每次回答时检索相关资料并加入模型上下文，不需要训练模型。它能够让模型使用特定比赛资料和教练案例，但不会自动赋予模型专业判断力。建议质量仍需要从检索是否正确、证据是否充分和实际编排是否合适三个层面验证。[Spring AI RAG 文档](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)

### 知识和个人记录

| 信息 | 内容 | 读取方式与作用 |
| --- | --- | --- |
| 比赛规则与分值 | 对应赛季、组别、节目、补充通知、例外条款及来源位置 | 先按已选比赛与版本确定范围，核心规则直接载入；检索附加解释，不能只靠语义相似度 |
| 花滑技术与教练案例 | 动作解释、连跳安排、疲劳取舍、失误补救、教练修改原因及适用对象 | 语义与关键词混合检索，选择与当前问题、水平和状态相符的材料 |
| 选手长期档案 | 单跳与连跳选择、明确偏好、训练事实、既有方案和教练修正 | 核心事实从业务库直接读取，历史细节按用户范围检索，不依赖最近几轮聊天 |
| 当前情境 | 本次比赛、今天的状态、正在修改的主方案及实际失误 | 随本次请求提供，按明确范围覆盖旧状态；不把临时疲劳自动写成永久能力 |
| 视频证据 | 原始片段位置、云端观察、用户补充和纠正 | 按当前选手与相关动作读取；观察与长期能力推断分开 |

原始资料进入服务端后，由解析和云端 LLM 保留标题、表格关系、条件、例外及页码或时间戳，生成内部索引。正文与脚注、规则与例外应能一起检索，不能机械按长度截断后丢失适用条件。用户不需要为索引字段填写表格。资料修订后，保存新版本并更新索引；旧方案仍可回溯当时的依据。

首批知识优先覆盖已选比赛规则、可信技术资料及少量有解释的教练案例。案例同时保留适用条件和不适用条件。泛泛的网上意见、未经复核的模型总结不自动成为事实依据；个人信息不进入其他用户可检索的公共知识库。

### 检索与推理过程

1. 服务端读取当前选手的核心档案、主方案和比赛上下文。用户身份与可访问资料范围由服务端确定，不由 LLM 决定。
2. LLM 将问题拆成相关检索任务，例如规则、后半程连跳案例、本人最近训练记录。简单请求直接检索，复杂问题允许继续查找原文和关联条款。
3. 对比赛版本、用户归属等明确范围先过滤；动作代码和组合顺序用规范化的精确或关键词匹配，语义表达使用托管 Embedding 与 pgvector 检索。两路结果合并去重，必要时用云端重排。`3S+3T` 与 `3T+3S` 不因语义接近而当成同一动作。
4. 将相关证据、当前状态和任务一起交给 LLM，生成候选编排、对比理由与失误预案。检索无结果时继续改写查询或解释缺口，不拿相似但不适用的赛季规则凑答案。
5. 模型调用服务端计分与明确条件检查工具，读取真实计算结果并修订；复杂规则仍由系统继续处理。工具负责分值和条件，编排偏好由情境推理决定。
6. 输出可编辑的编排结果及简洁依据。引用定位到原始规则或案例；在内部检查引用是否支持结论，不能把“附了引用”当作正确证明。

检索约束是系统内部正确选材的责任，不构成用户输入格式门槛。无需首版实现知识图谱或多个向量数据库；先以 PostgreSQL 保存业务事实和原文元数据、pgvector 保存向量，用规范化词项与关键词匹配补足动作代码检索。中文分词、缩写和多语言术语需要在测试集验证，不假设默认全文分词能直接满足需求。[Spring AI PGvector 支持](https://docs.spring.io/spring-ai/reference/api/vectordbs/pgvector.html)

### 不训练的持续改进

用户说“今天比较累”时更新本次状态；说“我已经稳定掌握这个连跳”时保留其自述来源并更新相关档案；教练纠正推荐时保存原条件、候选、修改和理由，供下一次检索。模型观察与用户陈述有矛盾时保留两者并解释，不能静默覆盖明确输入。

完整聊天记录、当前对话上下文和长期个人档案分别保存。只保留最近若干条消息不能实现长期个性化，全部聊天无差别塞入上下文也会混入过期信息。Spring AI 的聊天记忆提供上下文管理机制，但不替代业务档案及完整历史存储。[聊天记忆文档](https://docs.spring.io/spring-ai/reference/api/chat-memory.html)

对教练反馈的利用在本路线中表现为更新案例库、检索策略、提示和档案，不训练排序模型、不做 DPO 或其他微调。用户体验保持动作编辑和主编排/预案页面，LLM 与 RAG 是后台能力，不把产品改成只有聊天框的问答机器人。

### Hugging Face 上的花滑专用权重

检索到 [Mercity/figure-skating-transformer](https://huggingface.co/Mercity/figure-skating-transformer)、[figure-skating-gcn](https://huggingface.co/Mercity/figure-skating-gcn) 和 [figure-skating-ctm](https://huggingface.co/Mercity/figure-skating-ctm)。它们从骨架序列识别动作，公开模型卡与 checkpoint，不是直接接收视频、评估能力并规划编排的模型。

其中 Transformer 模型卡标注 `proprietary-internal`；架构源码未包含在仓库，需要原项目代码才能重建并加载权重。其自报细分类测试 accuracy 为 0.8348，macro-F1 为 0.4642。两个指标的差距提醒我们检查各类跳跃的表现，而不能仅凭整体准确率选型。上述结果来自作者私有数据划分，本轮没有复现。该系列不进入首版直接集成名单。

[WarmGPT](https://github.com/charlesl3/warmedge-chatbot) 是花滑领域检索增强问答项目，包含用户状态与对话处理，可借鉴交互思路；它没有提供本项目所需的完整编排求解和视频能力评估基线。资料检索能改善知识依据，不能单独解决个性化决策。

## 建议引擎设计

### 个体证据与状态

保存选手的原始表达、训练片段及时间位置、教练修正和实际完成记录。内部区分可观察事实、个人偏好、暂时状态与模型推断，并保留来源、适用情境和时间。模型推断可以修订，不直接覆盖明确的用户信息。

例如，“这段片子里完成了一次 3S+3T”只支持一次观察。它不能单独支持“长期成功率很高”或“后半程也能稳定完成”。主动上传的成功集锦还可能遗漏失败尝试。疲劳需要结合连续训练、动作前后变化和用户反馈，不能从单个姿态直接给出确定的生理疲劳值。

### 候选生成与情景比较

1. 由推理模型读取比赛资料、选手证据与偏好，提出若干安排思路，例如连跳提前、减少后段负担、保留原有顺序。
2. 模型调用计分、动作替换、局部搜索和规则工具，形成可计算的候选；工具反馈冲突和具体影响，模型据此修订。搜索需要保留不同取舍的方案，不能只按 BV 预筛掉更适合选手的候选。
3. 对候选推演漏接、降周、后段状态下降和继续原计划等情景。数据充分时估计条件概率；不足时用定性假设和范围比较，明确结果对假设是否敏感。
4. 模型基于证据比较候选，指出差别，必要时继续搜索。自动复检分值、显式约束和说明与数据是否一致；高风险争议交给用户或教练作具体判断。
5. 输出主编排、预案和可核对的取舍解释，并记录用户修改。模型间意见一致仅作辅助，不能当作正确性的证明。

首版不采用统一的“BV × 权重 + 稳定性 × 权重 − 疲劳 × 权重”决策公式。固定加权可以保留为实验对照。规则计算负责确定分值与明确条件，模型负责情境理解、候选策略和比较；内部工具格式不要求用户填写。

复杂规则可以由 Agent 继续解析、扩展计算与解释；在缺失或冲突资料下给出带假设的候选，避免静默套用已知模板。即使使用程序生成，也需要独立的规则案例验证，不能让生成模型自行宣称正确。

### 用教练反馈更新上下文

先收集“在同一选手、同一比赛和状态下，教练为什么选择方案 A 而非 B”及其修改记录。用户选择反映个人意愿，教练评价提供专业判断，实际训练结果反映可执行性，三者分别记录，不能混成一个点击率标签。

使用有来源的案例检索与模型推理，把修正写回案例及选手档案。当前不训练排序模型，不进行监督微调、DPO 或强化学习。专业性通过更好的知识、适用情境、检索和验证逐步改善，不承诺仅凭角色提示或 RAG 自动达到真实教练水平。

## 视频处理方案

建议采用服务端“整段粗看、动作片段细看、证据汇总”的流程。Android 只上传视频与用户描述并展示进度和结果；服务端定位片段、保留帧时间信息并调用云端多模态模型。粗定位也可能漏检，因此需要用完整片段的标注测量召回，并允许用户直接指定关注位置。当前不训练或部署专用视觉模型，不让用户手机运行姿态分析或推理服务。

视频结论应包含：片段范围、观察到的动作或中断、支持判断的画面、不能确定的部分，以及它对当前建议的影响。不能以一个“水平 85 分”替代可追踪的事实。

| 任务 | 预研优先级 | 主要验证条件 |
| --- | --- | --- |
| 定位跳跃或连跳片段、发现明显中断 | 高 | 远景、多人、遮挡、机位变化下的漏检与误报 |
| 区分跳种和周数类别 | 高 | 专用类别指标，与教练逐段标注比较，不能只测总准确率 |
| 起跳和落冰时刻、腾空时间 | 中 | 保留原始时间戳，验证帧级误差，区分原速与慢放 |
| 个人稳定性及前后段差异 | 高，但需要多次观察 | 尝试次数、成功与失败样本、情境和时间范围 |
| 精确判刃、欠周、绝对高度、自动 GOE | 单独研究 | 关键细节是否可见、拍摄条件和尺度信息，不能从通用模型能力外推 |

默认静态 1 FPS 可能完全错过快速动作的关键过程，模型窗口更长也不能恢复未采样到的画面。系统应处理用户实际提供的视频，不用拍摄要求阻挡输入；画面不足时分析可见部分，解释不确定性并允许补充。保留原始帧时间信息，避免重编码或慢动作播放造成计时错误。

上传视频默认用于用户本次分析与其授权保存的历史；将视频或标注用于通用模型训练应当作为另一个明确选择，不由一次分析授权推导。原始视频保存在受控对象存储，业务记录使用引用及必要片段，不把视频写进 Git。

## 工程实现建议

| 部分 | 建议 | 理由与边界 |
| --- | --- | --- |
| Android | Kotlin + Jetpack Compose | 仅做原生输入、上传、编辑、展示；不部署推理或分析服务，[官方说明](https://developer.android.com/compose) |
| 业务与 Agent 后端 | Java + Spring Boot，先做模块化单体 | 用 HTTP/SDK 调用托管 LLM、Embedding 和按需重排接口；[Spring AI](https://docs.spring.io/spring-ai/reference/api/tools.html)为可选适配，不让框架绑定业务状态 |
| 计算工具 | Java 服务端计分与明确条件检查；局部搜索按需增加 | 为 LLM 提供可靠结果，不以固定权重决定个人推荐；OR-Tools 不是首版前置依赖 |
| 视频任务 | Java 任务协调与独立媒体处理 worker，调用 FFmpeg 等工具 | 长任务保存进度、失败原因与结果引用；原视频分析可复用，不因拖动一行反复上传处理 |
| 数据与检索 | PostgreSQL + pgvector + 对象存储 | 业务事实、规则与知识版本、个人档案、向量及视频引用；精确或关键词与语义检索结合 |
| 可选专用模型 | 当前不实施，仅保留参考 | 不增加模型训练、微调、端侧部署或 ONNX 转换工作 |

后端不用 Python 的约束保持不变。当前直接调用托管模型与检索服务，不复现 PyTorch 训练流程，不自建 Python 推理服务。知识入库使用已有 Embedding 模型生成向量，是推理和索引构建，不是模型训练。

效率上将即时编辑与深度分析分开：已理解规则下的 BV 更新走计算工具；个性化重新推荐走模型任务；视频上传与分析走可恢复的后台任务。缓存绑定视频内容、模型版本及处理参数；方案建议还绑定规则和能力版本，防止返回过期结果。暂不承诺未测量的并发量、单次价格或时延。

## 选型实验

第一轮可采用 30 至 50 段真实手机片段和 20 至 30 组完整编排情景作为探索性实验规模，后续按错误类型扩充。数量是工作量建议，不足以单独证明上线可靠性。覆盖初学到较高水平、不同机位、连跳失败、遮挡和疲劳描述；不只使用清晰的比赛转播或成功片段。

| 实验 | 对照与测量 | 决策用途 |
| --- | --- | --- |
| 视频理解 | Gemini、Qwen3-VL、关键帧视觉模型；相同片段比较事件定位、跳种与周数 macro-F1、每类误差、无法判断的比例 | 选择视频模型与抽样策略；置信判断同时检查是否匹配实际错误率 |
| 检索质量 | 规则、例外、同名赛事不同赛季、动作顺序、中英文别名、历史修正等有依据的问题 | 检查应找到的证据是否找全、过期与跨用户资料是否被排除，以及引用是否支持结论 |
| 编排建议 | 同一云端 LLM 下，对比无知识检索、知识 RAG、知识 RAG 加个人档案；计算工具保持一致 | 由教练盲评可执行性、偏好匹配、补救质量和依据，分清检索与个性化各自的收益 |
| 排序贡献 | 端到端候选生成与固定候选集排序分开比较 | 区分收益来自更好的候选搜索还是模型比较，避免将两者混为一谈 |
| 一致性 | 同一条件重复运行，交换候选顺序，仅改变疲劳描述或位置偏好 | 检查推荐是否响应真实条件，以及是否被措辞、排序位置或随机性支配 |
| 事实与计算 | 规则案例、已有主方案、实际失误前缀、手算分值对照 | 确认没有遗漏硬限制、修改已发生动作或编造分值 |
| 性能成本 | 分别记录入库、检索、重排、视频理解、编排推理、计算耗时及用量 | 选择云端模型、上下文规模、缓存与任务拆分方式，不转向端侧推理 |

调试提示与案例库使用的样本和最终评测样本按选手、训练场次及来源视频隔离，避免把测试标准答案加入案例库后再声称提升。教练意见不一致时保留分歧，不能把主观任务伪装成唯一标准答案；检查检索与个人上下文是否改善教练评价，不能只检查解释是否流畅。

第一阶段交付应是能回放检索证据、个人上下文与计算结果的实验，明确 RAG 和个性化相对基线的提升及失败案例。后续投入用于补齐知识、改善检索与资料理解，不默认扩展到训练、微调或自建 GPU 服务。
