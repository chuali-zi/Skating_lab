# Skating Lab 计算与建议引擎技术调研

调研日期：2026-11-14。产品基线：[PRD v0.7](PRD.md)。

首版用户端已确定为原生 Android。建议引擎采用云端多模态模型理解资料与选手情境，结合可重复计算的计分工具、候选搜索和失误情景推演；通过教练反馈逐步学习方案偏好。现有花滑研究可为动作识别和质量分析提供基础，但本轮未找到经验证、可以直接完成个人能力评估和完整编排建议的端到端开源模型。

本轮核对了论文、官方仓库、模型卡与厂商文档，没有执行模型推理或训练。下述优先级是进入实测的顺序，不是实测性能排名。用户视频、API 访问能力、测试 GPU 及教练标注样本尚未在本轮建立。

## 决策范围

| 状态 | 内容 |
| --- | --- |
| 已确认 | 原生 Android；不采用 Web 或网页套壳；后端不使用 Python；允许云端模型；自由资料由系统处理 |
| 已确认 | 推荐考虑选手能力、稳定性、疲劳和偏好，不以理论 BV 或固定人工加权作为唯一决策 |
| 当前建议 | Kotlin + Jetpack Compose；Java 模块化后端；PostgreSQL 与视频对象存储；可更换的模型接口 |
| 需要验证 | 云端模型在花滑场景下的识别与建议质量；专用视觉模型的收益；能力与疲劳推断；成本和延迟 |
| 产品预研 | 用户训练视频作为能力证据，不默认承诺精确判刃、欠周和自动裁判能力 |

这些资源最接近的是“视频中发生了什么”和“已经完成的节目质量如何”。“下一场比赛这个人应该怎样安排”还需要个人历史、当前状态、目标和训练反馈。比赛转播中的精英运动员样本与普通选手的手机训练录像存在场景差异，需要按真实输入验证，不能直接沿用论文指标。

### Hugging Face 上的花滑专用权重

检索到 [Mercity/figure-skating-transformer](https://huggingface.co/Mercity/figure-skating-transformer)、[figure-skating-gcn](https://huggingface.co/Mercity/figure-skating-gcn) 和 [figure-skating-ctm](https://huggingface.co/Mercity/figure-skating-ctm)。它们从骨架序列识别动作，公开模型卡与 checkpoint，不是直接接收视频、评估能力并规划编排的模型。

其中 Transformer 模型卡标注 `proprietary-internal`；架构源码未包含在仓库，需要原项目代码才能重建并加载权重。其自报细分类测试 accuracy 为 0.8348，macro-F1 为 0.4642。两个指标的差距提醒我们检查各类跳跃的表现，而不能仅凭整体准确率选型。上述结果来自作者私有数据划分，本轮没有复现。该系列不进入首版直接集成名单。

[WarmGPT](https://github.com/charlesl3/warmedge-chatbot) 是花滑领域检索增强问答项目，包含用户状态与对话处理，可借鉴交互思路；它没有提供本项目所需的完整编排求解和视频能力评估基线。资料检索能改善知识依据，不能单独解决个性化决策。

| [MediaPipe Pose Landmarker](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker) | 提供人体关键点，支持图像、视频与 Android 集成 | 端侧姿态与取景质量的轻量基线 | 快速旋转、遮挡、远景和多人是否可靠；人体骨架不等于冰刀接触面识别 |

优先以云端 API 建立质量基线，不先购买 GPU。大型模型的完整部署开销包含权重、视觉编码、上下文缓存和执行框架，不能仅按参数量估算显存并承诺可部署。模型选择通过花滑样本比较决定，不以“最新”或“参数最多”替代验证。

## 建议引擎设计

### 个体证据与状态

保存选手的原始表达、训练片段及时间位置、教练修正和实际完成记录。内部区分可观察事实、个人偏好、暂时状态与模型推断，并保留来源、适用情境和时间。模型推断可以修订，不直接覆盖明确的用户信息。

例如，“这段片子里完成了一次 3S+3T”只支持一次观察。它不能单独支持“长期成功率很高”或“后半程也能稳定完成”。主动上传的成功集锦还可能遗漏失败尝试。疲劳需要结合连续训练、动作前后变化和用户反馈，不能从单个姿态直接给出确定的生理疲劳值。

### 候选生成与情景比较

1. 由推理模型读取比赛资料、选手证据与偏好，提出若干安排思路，例如连跳提前、减少后段负担、保留原有顺序。
2. 模型调用计分、动作替换、局部搜索和规则工具，形成可计算的候选；工具反馈冲突和具体影响，模型据此修订。搜索需要保留不同取舍的方案，不能只按 BV 预筛掉更适合选手的候选。
3. 对候选推演漏接、降周、后段状态下降和继续原计划等情景。数据充分时估计条件概率；不足时用定性假设和范围比较，明确结果对假设是否敏感。
4. 模型基于证据比较候选，指出差别，必要时继续搜索。自动复检分值、显式约束和说明与数据是否一致；高风险争议交给用户或教练作具体判断。
5. 输出主编排、预案和可核对的取舍解释，并记录用户修改。模型间意见一致仅作辅助，不能当作正确性的证明。

首版不采用统一的“BV × 权重 + 稳定性 × 权重 − 疲劳 × 权重”决策公式。固定加权可以保留为实验对照。规则计算负责确定分值与明确条件，模型负责情境理解、候选策略和比较；内部工具格式不要求用户填写。

复杂规则可以由 Agent 继续解析、扩展计算与解释；在缺失或冲突资料下给出带假设的候选，避免静默套用已知模板。即使使用程序生成，也需要独立的规则案例验证，不能让生成模型自行宣称正确。

### 用教练反馈学习偏好

先收集“在同一选手、同一比赛和状态下，教练为什么选择方案 A 而非 B”及其修改记录。用户选择反映个人意愿，教练评价提供专业判断，实际训练结果反映可执行性，三者分别记录，不能混成一个点击率标签。

冷启动先做有来源的案例检索与模型推理。有足够可靠标注后，训练候选排序模型；再评估是否需要对生成模型进行监督微调或偏好优化。[DPO 原论文](https://arxiv.org/abs/2305.18290)证明了从比较偏好优化语言模型的一种方法，但并未验证花滑建议，不能把方法名称当成效果保证。首版不预设强化学习训练工程。

## 视频处理方案

建议采用“整段粗看、动作片段细看、证据汇总”的流程。整段分析定位训练阶段与疑似动作，细看阶段围绕目标动作保留更密集的原始帧和人体局部信息，再由专用模型或多模态模型分析。粗定位也可能漏检，因此需要用完整片段的标注测量召回，并允许用户直接指定关注位置。

视频结论应包含：片段范围、观察到的动作或中断、支持判断的画面、不能确定的部分，以及它对当前建议的影响。不能以一个“水平 85 分”替代可追踪的事实。

| 任务 | 预研优先级 | 主要验证条件 |
| --- | --- | --- |
| 定位跳跃或连跳片段、发现明显中断 | 高 | 远景、多人、遮挡、机位变化下的漏检与误报 |
| 区分跳种和周数类别 | 高 | 专用类别指标，与教练逐段标注比较，不能只测总准确率 |
| 起跳和落冰时刻、腾空时间 | 中 | 保留原始时间戳，验证帧级误差，区分原速与慢放 |
| 个人稳定性及前后段差异 | 高，但需要多次观察 | 尝试次数、成功与失败样本、情境和时间范围 |
| 精确判刃、欠周、绝对高度、自动 GOE | 单独研究 | 关键细节是否可见、拍摄条件和尺度信息，不能从通用模型能力外推 |

默认静态 1 FPS 可能完全错过快速动作的关键过程，模型窗口更长也不能恢复未采样到的画面。系统应处理用户实际提供的视频，不用拍摄要求阻挡输入；画面不足时分析可见部分，解释不确定性并允许补充。保留原始帧时间信息，避免重编码或慢动作播放造成计时错误。

上传视频默认用于用户本次分析与其授权保存的历史；将视频或标注用于通用模型训练应当作为另一个明确选择，不由一次分析授权推导。原始视频保存在受控对象存储，业务记录使用引用及必要片段，不把视频写进 Git。

## 工程实现建议

| 部分 | 建议 | 理由与边界 |
| --- | --- | --- |
| Android | Kotlin + Jetpack Compose | 原生界面、编辑与视频交互；Compose 是官方推荐的原生 UI 工具包，[官方说明](https://developer.android.com/compose) |
| 业务与 Agent 后端 | Java + Spring Boot，先做模块化单体 | 用普通 HTTP/SDK 调用云端模型；工具调用可使用 [Spring AI](https://docs.spring.io/spring-ai/reference/api/tools.html)，不让框架绑定业务状态 |
| 计算工具 | Java 计分、规则评估、局部搜索；适合形式化的部分用 OR-Tools Java | 求解器负责已定义问题，推荐质量仍取决于选手模型和候选策略，[官方 Java 支持](https://developers.google.com/optimization/install/java) |
| 视频任务 | Java 任务协调与独立媒体处理 worker，调用 FFmpeg 等工具 | 长任务保存进度、失败原因与结果引用；原视频分析可复用，不因拖动一行反复上传处理 |
| 数据 | PostgreSQL + 对象存储 | 保存证据、状态、版本和对比记录；模型调用与分析任务可恢复 |
| 可选专用模型 | 托管推理优先；经过验证的小模型可研究 ONNX Runtime Java/Android | [ONNX Runtime Java](https://onnxruntime.ai/docs/get-started/with-java.html)提供 Java 调用，但具体模型能否导出、算子兼容与数值一致性必须验证 |

后端不用 Python 的约束保持不变。多数花滑研究代码使用 PyTorch/Python，不能声称复制仓库就能在 Java 中运行。首版调用托管模型，不自建 Python 推理服务；后续如需复现训练代码，应单独说明研究环境依赖与成本，不能偷偷把 Python 服务纳入生产路线。ONNX 只适用于实际验证可以导出并正确运行的模型，不预设整个 Mamba 或多模态大模型都可直接转换。

效率上将即时编辑与深度分析分开：已理解规则下的 BV 更新走计算工具；个性化重新推荐走模型任务；视频上传与分析走可恢复的后台任务。缓存绑定视频内容、模型版本及处理参数；方案建议还绑定规则和能力版本，防止返回过期结果。暂不承诺未测量的并发量、单次价格或时延。

## 选型实验

第一轮可采用 30 至 50 段真实手机片段和 20 至 30 组完整编排情景作为探索性实验规模，后续按错误类型扩充。数量是工作量建议，不足以单独证明上线可靠性。覆盖初学到较高水平、不同机位、连跳失败、遮挡和疲劳描述；不只使用清晰的比赛转播或成功片段。

| 实验 | 对照与测量 | 决策用途 |
| --- | --- | --- |
| 视频理解 | Gemini、Qwen3-VL、关键帧视觉模型；相同片段比较事件定位、跳种与周数 macro-F1、每类误差、无法判断的比例 | 选择视频模型与抽样策略；置信判断同时检查是否匹配实际错误率 |
| 编排建议 | 规则与固定权重基线、纯 LLM、模型加计算工具三组；相同输入和预算 | 由教练盲评可执行性、偏好匹配、补救质量和解释依据，允许平局与分歧 |
| 排序贡献 | 端到端候选生成与固定候选集排序分开比较 | 区分收益来自更好的候选搜索还是模型比较，避免将两者混为一谈 |
| 一致性 | 同一条件重复运行，交换候选顺序，仅改变疲劳描述或位置偏好 | 检查推荐是否响应真实条件，以及是否被措辞、排序位置或随机性支配 |
| 事实与计算 | 规则案例、已有主方案、实际失误前缀、手算分值对照 | 确认没有遗漏硬限制、修改已发生动作或编造分值 |
| 性能成本 | 分别记录上传、预处理、视频推理、编排推理、计算耗时及用量 | 选择端侧、云端、小模型或缓存的实际收益 |

训练与评估按选手、训练场次和来源视频隔离，避免相邻帧或同一片段进入两侧。教练意见不一致时保留分歧，不能把主观任务伪装成唯一标准答案。个体概率模型需要检查预测校准；偏好模型需要看是否改善教练选择与后续训练结果，不能只检查解释是否流畅。

第一阶段的交付应是能回放证据与计算过程的实验结果，并指出混合方案相对两个基线的提升及失败案例。只有证明模型有用，再决定训练专用模型、部署 GPU 或扩大自动化范围。
