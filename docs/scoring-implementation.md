# Java 计分模块首版实现

2026-11-14。实现位置：[ScoringModels](../server/src/main/java/com/skatingcoach/scoring/ScoringModels.java)、[ScoringService](../server/src/main/java/com/skatingcoach/scoring/ScoringService.java)。产品语义依照 [PRD](PRD.md) 和[架构设计](architecture.md)。

该模块使用 Java 17 与 BigDecimal，提供可重复运行的算术、明确条件检查和预案前缀保护。模块本身不调用 LLM、不估算个人成功率、不生成固定加权排名，也没有内置某个赛季的通用分值或比赛规则。用户资料由上层理解后传入内部契约，用户不需要填写这些结构。

## 已实现的入口

| 方法 | 输入 | 输出 |
| --- | --- | --- |
| `evaluate` | 有序元素、明确规则快照、可选动作范围 | 逐跳/逐行试算、可确定时的总 BV、条件检查 |
| `evaluateRecovery` | 权威实际完成前缀、完整预案、规则、后续可选范围 | 前缀是否保持、冻结数量与评分结果 |
| `compare` | 同一规则下的两个方案与个人可选范围 | 动作、顺序、类型、时间变化，以及可确定时的 BV 差值 |
| `defaultFailureScenario` | 主方案与规则 | 可确定最高 BV 连跳时，产生第一跳完成但后续未接上的假设情景；并列取出场靠前者 |

HTTP 适配由后端框架提供在 `/api/v1/scoring` 下。该包是普通 Java，可单独测试；身份验证、权威规则来源与方案保存不在该包内部实现。

## 计分与时间语义

元素字段为 `id`、`type`、`jumps`、`plannedStartSeconds`。`type` 为 `SINGLE / COMBINATION / SEQUENCE`；`jumps` 是有序动作编码数组。已知动作大小写和 `Eu` 别名可归一化，Euler 采用 `1Eu`；具体分值只从调用者提供的规则快照读取，零分是合法值，不回退到旧赛季默认值。

每行按跳跃分值相加，再应用元素类型系数、适用的后半程系数，最后按规则指定的位数与方式舍入；方案总计累加这些行值。连续跳的系数必须明确提供，不假设所有赛季均为某个固定值。

后半程条件分开表达：

- 时间阈值和是否包含边界，依据计划执行秒数判定。
- 适用元素类型及可选的完整动作组合范围。
- 最后若干元素的资格窗口；该窗口先按方案位置确定，再检查时间。
- 奖励名额上限及按出场先后或倒序分配的顺序。

未知时间不能通过行号推断为后半程。有奖励名额限制时，前一元素资格未知也可能使后续元素是否得到名额不确定；模块传播这种不确定性，不抢先给后一元素认定加成。

## 规则与结果的范围

`RuleSet` 包含 `id/version/sourceReference`、动作分值、后半程规则、连续跳系数、数量和重复条件、舍入方式、覆盖状态与未解决条款。

数量条件以 `CountLimit` 表达：对象缺失表示未知；`unrestricted=true` 明确表示不限制；`maximum` 表达已知上限。缺少规则不会自动解释为无限制。重复限制和必需动作只核对调用者明确提供的内容；没有实现完整 ISU 重复、无效元素、特殊标记或 GOE/PCS 裁判规则。

`Evaluation` 中：

| 字段 | 含义 |
| --- | --- |
| `baseTotal` | 已知原始动作 BV 的合计，缺少任一动作分值时为空 |
| `knownSubtotal` | 在已表达条件下能够进行的逐行试算之和；不能代替完整总 BV |
| `evaluatedTotal` | 全部相关计值、规则覆盖和已知违规后果均可确定时的总 BV；否则为空 |
| `scoreComplete` | 本次是否能够给出确定的总 BV |
| `checksComplete` | 所有提供的检查是否已获得明确结果；不等于方案通过检查 |
| `hasViolations` | 是否违反了已明确的条件 |
| `checks` | 每项检查的 `SATISFIED / VIOLATED / UNKNOWN`、动作行、解释与规则来源 |

存在未解决条款或覆盖未完成时，保留逐行试算，但不会给出确定总 BV。出现超出元素数量或重复上限等问题时，不擅自猜测“多余元素计零”或某个扣分公式；输出 `SCORING_CONSEQUENCE_UNKNOWN`，等待知识/规则模块提供完整解释。

独立单跳、完整连跳和连续跳候选分开检查。取消单跳 3T 不影响已选 `3S+3T`；明确全局排除 3T 才影响所有包含它的未来候选。有序组合不同即为不同候选，选中并不意味着必须使用。

## 失误前缀与比较

预案验证保持已发生前缀的动作行 ID、类型、有序动作和时间。数值相同的 `90.0` 与 `90.00` 视为相同时间。前缀遭到改写时 `prefixPreserved=false`，并且不给确定预案总 BV。

服务端必须从保存的失误情景中读取实际完成前缀，不能让模型通过同时改写请求中的前缀和预案来绕过保护。用户新建或修改实际失误情景是单独的产品操作。已经实际完成的降周动作不再按未来可选列表排除，但仍计入比赛规则与重复检查。

默认失误情景是明确标注的假设，不自动写成真实训练经历。若无法确定连跳的 BV 或规则覆盖，方法返回空结果，由界面说明尚不能自动选定；用户仍可手动指定情景。比较入口只返回变化和可确定的 BV 差值，不把理论分值变化解释为个人收益变化。

## 验证与后续范围

单元测试位于 [ScoringServiceTest](../server/src/test/java/com/skatingcoach/scoring/ScoringServiceTest.java)，使用清楚标注的合成规则 fixture。测试覆盖时间边界、窗口与奖励上限、未知资格传播、组合舍入、单跳与连跳独立选择、全局排除、规则缺失、Euler 零值、别名冲突、未解决条款、冻结实际前缀、默认失误和方案差异。

本轮以 JDK 17 执行 `mvnw -B --no-transfer-progress -Dtest=ScoringServiceTest test`，18 项测试全部通过，失败、错误和跳过均为 0。此结果验证模块的明确契约，不代表真实比赛规则、模型建议或 Android 全链路已完成验收。

生产比赛规则需要知识管理模块从适用赛季及组别的权威来源构建并验证。本模块当前不会把测试 fixture 或仓库旧 SQL 种子自动发布为正式比赛规则。更多规则的执行表达和违规计值策略可在明确来源及案例后逐项扩展。
